## 2. 分优先级增量改造清单

### 🔴 紧急改造（立刻做，不做会持续产生补丁逃逸、轮次爆炸）

#### E-01：统一 S3 回流重试上限，消除配置-文案矛盾

**根因**：YAML work_manual 写"驳回最多 3 轮"，顶层 max_s3_retries:20；实测会烧满 20 轮才锁死，放大补丁叠加风险。

**变更对象**
- wenstaros_core_repair_flow.yaml：顶层全局参数；S3 阶段 work_manual
- FlowEngine/StageRunner/S3 conditionGateCheck.ts

**实现方案**
1. 将 S3 专属重试配置 max_s3_retries 从 20 修改为 3；YAML 注释、work_manual 文案同步统一。
2. 保留全局 max_stage_retries:20 作为全流水线全局熔断，与 S3 单阶段重试解耦：
   - max_s3_retries：仅控制 S3 代码落地阶段回流重试；
   - max_stage_retries：任意 stage 全局最大轮次，防止全流程死循环。
3. S3 阶段输出日志字段：s3_cycle_count，每一轮自增，写入 audit 卷宗。

**验收标准**
- S3 累计重试达到 3，触发 condition gate 失败，不会继续进入下一轮 S3 编码。
- audit 卷宗每一条 S3 运行记录携带 s3_cycle_count。
- YAML 文档注释、work_manual、代码内配置三者数值完全一致。

**影响范围**：仅 S3；不改动 S1/S2/S4-S7 业务逻辑。

#### E-02：S3 累计回流≥3 轮强制跳转 S1-S2 重审架构方案

**根因**：到达重试上限之后直接终止会丢失上下文；需要强制回到架构预分析环节，禁止持续在编码层叠加补丁。

**变更对象**：FlowEngine/determineNextStage.ts DFA 状态机；S3 conditionGateCheck.ts

**实现方案**
1. S3 每轮结束，若 passed=false：
   - 判断条件：s3_cycle_count >= max_s3_retries
   - ✅触发分支：不直接 abort 终止流水线，DFA 强制跳转回 S1→S2
   - 生成机器信号：signal: s3_stuck_in_patch_loop=true，写入 audit 卷宗。
2. 将全部 S4/S4.5 历史驳回证据、diff 变更、CK 完整报告完整注入 S2 的 inject_global_memo 全局备忘录。
3. S2 人工闸门强制要求：必须重新输出补丁 / 架构优化两套方案；解释连续三轮编码无法满足架构约束的根因；必须明确选择重构方案，或者登记技术债务走补丁豁免流程。
4. 只有 S2 再次审批通过新的 s2_evidence，才允许再次进入 S3。
5. 哨兵日志输出告警：WARN: S3 陷入补丁循环，强制回退架构重审。

说明：不是报错结束，是强制回流到架构思考环节，完整保留全部上下文。

**验收标准**
- 构造测试用例：连续 3 轮 S3 被 S4 驳回；流水线自动回 S1-S2。
- S2 全局备忘录完整携带全部历史驳回证据。
- 没有直接 abort，完整保留运行卷宗。

**影响范围**：DFA 流转逻辑；S2 备忘录注入；不改动其他 stage 内部逻辑。

### 🟠 高优先级改造（解决四大核心漏洞：归档无校验、验证闭环缺失、债务台账、证据截断、S3 写硬闸）

#### H-01：S7 变更归档增加 Delegate 机器校验（补齐全流程最后一道机器闸门）

**根因**：现状 S7 只有 Agent 人工写归档卷宗，没有机器核验，台账、回滚清单、修复总结可能漏写、错写；无 Delegate 兜底。

**变更对象**
- YAML S7 阶段：新增 delegate 子步骤；
- 新增：DelegateReviewer/S7ArchiveValidator.ts；
- audit 卷宗 schema 扩展。

**实现方案**
1. S7 拆成两个子 stage：
   - S7-A：Agent 执行原有逻辑，产出归档产物：变更摘要、回滚清单、验证清单、修复总结、债务标记、三轮复审提示；输出结构化 json：s7_archive_payload；
   - S7-B【新增，delegate 机器校验】：独立 TS 委托评审，不调用 LLM，纯结构化校验。
2. S7-B 硬校验检查项：
   - ✅必填字段完整性：change_summary / rollback_plan / verification_checklist / debt_marker / audit_ref 全部非空；
   - ✅debt_marker 校验：如果本次运行标记为【补丁方案】，必须附带 debt_item_id（指向 tech_debt_ledger），并且填写还债计划、计划归属 P0/P1/P2 里程碑；补丁不允许无登记直接放行；
   - ✅校验回滚清单：涉及修改的文件列表，必须和 S3 全部 diff 文件集合完全匹配，不能出现文件漏记；
   - ✅校验：若 S4.5 打分 < 98，必须有对应的豁免记录 exemption_id 来自 exemptions.json；无豁免直接 S7 gate 失败；
   - ✅大重构标记：如果变更属于大重构，强制校验 three_round_review_plan 不为空；
3. S7-B 输出：
   - archive_valid: true/false；
   - archive_validation_errors[]；
   - 只有 S7-B 机器校验全部通过，本次 harness run 状态标记为 run_status=completed；否则为 run_status=archive_invalid，返回 S7-A 重新补全归档产物。
4. audit 卷宗增加 s7_archive_validation_report 字段。

**验收标准**
- 故意缺填回滚清单、补丁不登记债务；S7-B 机器校验拦截，不会标记运行成功。
- audit 卷宗持久化 s7_archive_validation_report。

**影响范围**：仅 S7；不改动前面 S1-S6 业务。

#### H-02：S6 功能验证：消除"参考"落差，明确机器闭环与人工责任边界

**根因**：原设计 WebUI 三场景、DB 标注率、停服重启降级为参考；流水线闭环能力与 CLAUDE.md 复审铁律不一致；一部分机器能跑，一部分只能人工。

**变更对象**：S6 YAML、S6 执行器、schema。

**实现方案**
- 原则：不强行把全部行为测试自动化（成本极高），而是做「强制分层契约」，区分【机器可自动化】与【人工外部验证项】，禁止全部降级为参考。
1. S6 拆分为 S6-A【机器自动化验证】、S6-B【人工外部验证契约】；
2. S6-A（机器必跑，条件 gate，不通过直接失败）：
   - tsc 编译、vitest 全量、CK-09 回归安全、CK-10 意图达成、save() 落盘 grep 审计、数据库基础一致性审计；全部原有脚本层能力，强制必跑，不再是参考；
3. S6-B（人工外部验证契约，机器做任务单生成，不自己执行）
   - 机器无法自动化的项目，流水线生成标准化人工验证任务单，作为 run 卷宗强制附属产物；不人工完成，run 状态标记为 await_manual_verification，不能进入 S7 完成归档；
   - WebUI 三场景：对话 / 会晤 / 角色扮演；
   - DB 标注率抽样校验；
   - 停服-重启-数据库一致性三段式复审；
   - S6-B 产出结构化 manual_verification_ticket，字段：验证项清单、前置条件、预期结果、复现步骤、验收人、截止时间；
4. 放行分支：
   - S6-A 全部通过 + S6-B 人工任务单全部确认完成（导入人工确认签名）→ 进入 S7；
   - S6-A 全部通过，但 S6-B 尚未人工确认 → 流水线状态：await_manual_verification，阻塞 S7 归档；不能直接 complete；
   - S6-A 任意失败 → 直接回流 S3 修复；
   - 在 YAML 删除原注释"原规范仅作参考"，替换成分层契约文档。

**验收标准**
- S6-A 机器测试失败，无法进入 S7。
- S6-A 全部通过，但没有完成 S6-B 人工确认，run 不会 complete。
- audit 卷宗持久化 manual_verification_ticket 以及人工确认签名。

**影响范围**：S6 阶段；不会破坏现有脚本测试；只是增加人工任务单契约。

#### H-03：统一技术负债台账 tech_debt_ledger 建设

**根因**：当前债务信息散落在 audit 卷宗、CLAUDE.md、evolutionEngine pendingUpgrades，没有统一机器可查询的台账；补丁修复无法强制登记债务；无法跟踪债务状态、里程碑、趋势。

注意：该台账属于 harness 治理数据库，独立于 wenstar-cc 业务 SQLite；存放于 data/harness_db/harness_debt.sqlite。

**变更对象**：新建 DB schema；S2/S4.5/S7 三处采集点；查询 API；S2/S7 校验规则。

**核心采集时机（三处自动写入）**
1. S2 方案定稿：当 S2 人工审批选择【补丁方案】，强制插入 / 更新一条 debt 记录；必须填写：债务简述、根源分类、风险等级、关联里程碑（P0/P1/P2#8 等）、计划还债迭代、验证条件；不填写则 S2 gate 不通过；
2. S4.5 收敛闸门：DS 打分扣分点自动解析，识别出结构性债务候选，写入候选池；可以被 S2/S7 确认转正；
3. S7 归档校验（S7-B Delegate）：若本次 run 标记为补丁修复，校验必须存在对应 debt_id，否则归档校验失败；

**配套能力**
- 提供查询 API：按状态、里程碑、风险等级、产生时间筛选；输出债务趋势报表；
- 与 exemptions.json 豁免台账做关联：部分临时补丁需要豁免 DS 扣分，必须绑定一条 debt_id；
- 对接 P0-P3 路线图：台账每条记录绑定对应的里程碑编号；支持查询某个里程碑下全部未清零债务；
- 对接 audit 卷宗：每条 debt 反向关联多条 harness run 的 audit_ref；可以回溯每一笔债务是在哪一次流水线运行产生；
- 【远期 L-01】可以把台账变更同步写入知识库 knowledge_growth_log；本次仅预留字段，不实现调用。

**验收标准**
- 选择补丁方案的 S2 审批，不填写债务记录，S2 gate 拒绝通过。
- S7 归档补丁修复，如果找不到对应 debt_id，S7-B 校验失败。
- 可以 SQL 查询全部未清偿债务，关联到每一次流水线运行卷宗。

**根因**：现状 S4.5 大量 11 维评审、DS 打分、CK 详细报告保存在 audit JSON；回流到 Agent 仅返回精简 reject_reason 摘要；编码时丢失完整依据，反复踩坑。

**变更对象**：FlowEngine 的上下文注入模块；S4.5 输出 schema；audit 卷宗。

**实现方案**
1. S4.5 输出产物拆分为两份：
   - reject_reason_summary：简短摘要（兼容旧逻辑，用于日志展示）；
   - ✅新增 full_review_evidence：完整结构化评审证据，包含：11 维评审每一项明细、全部 CK-00~11 完整输出、DS-01~23 每条扣分条目（扣分点、原因、建议修复方向）、uuid 校验报告、耦合分析、风险标记；

3. S3 的 work_manual 增加强制条款：编码前必须阅读全局备忘录中 full_review_evidence 全部评审明细，不允许只看简短摘要。

**验收标准**
- 构造测试：S4.5 多条 DS 扣分；回流 S3；读取 S3 阶段的 global_memo，可以拿到全部 DS 扣分明细、11 维评审原始条目。
- audit 卷宗同时保存 summary + full 两份证据。

#### H-05：S3 写文件硬防护：拦截无约束整文件重写，补齐"禁止大段覆写"机器闸门

**根因**：现状 S3 仅靠 prompt 要求增量 diff 编辑；YAML 开启 write_file:true，引擎无硬闸；Agent 可以直接整文件覆写，破坏增量修复原则。

目标：不是彻底禁止 write_file；而是区分「增量 diff 编辑」和「全文件覆写」，对全文件覆写施加强约束。

**变更对象**：ToolWhitelistGuard；S3 工具调用审计；diff 分析器；S3 YAML。

**实现方案**
1. 在 ToolWhitelistGuard 为 S3 新增写操作审计计数器 + diff 变更分析器：
   - 每一次文件写入，计算：原始文件 size vs 写入后 size；统计新增 / 修改行数占总文件比例；
   - 定义可配置阈值：large_rewrite_threshold_ratio = 0.7；单文件变更行数占比 >70%，判定为【疑似整文件重写】；配置项放全局 config，禁止硬编码。
2. 出现疑似整文件重写，分两条分支：
   - 分支 A：当前 S3 是普通补丁 / 局部修复任务 → 直接工具 guard 拒绝执行写入；返回机器错误：S3_FORBID_FULL_FILE_OVERWRITE：S3 增量修复禁止整文件覆写；如需大规模重构，请回到 S2 把任务归类为结构性重构，走重构专项流程；
   - 分支 B：S2 的 s2_evidence 方案已经显式声明该文件会大规模重构，并且在 S2 审批时人工确认，携带 allow_full_rewrite:["src/xxx.ts"] 白名单；则放行；同时写入 audit 告警日志；
3. S3 work_manual 更新说明该硬闸规则。
4. 保留 diff 原始变更记录，写入 audit，记录每一个文件的变更占比、是否触发大改写告警。

**验收标准**
- 普通修复任务，尝试整文件覆写，工具守卫直接拦截，不会落盘。
- S2 审批证据预先声明允许大文件重写并加入白名单，才允许执行。
- audit 卷宗记录每个文件变更占比、是否触发大改写告警。

- **阶段 2：🟠高优先级分批实现（H-05 → H-04 → H-03 → H-02 → H-01）**：建议顺序：S3 写防护 → S4.5 证据注入 → 债务台账 DB + 采集点 → S6 分层验证 → S7-B 归档校验；每完成一项，跑对应回归用例。

### 风险提示

- **DFA 改动风险**：E-02 修改 determineNextStage 跳转逻辑；务必保证原有正常 S3 成功的路径完全不受影响；回归用例必须包含：正常 S3 一次就通过的正向用例。
- **审计卷宗兼容性风险**：所有新增字段全部为可选新增字段；旧版本产生的 audit 卷宗，新版本解析不能报错；新增 DB 表为新增独立表，不修改原有业务表结构。
